<design_decision>
## Pairing bootstrap — CHOSEN: CLI/instance-surfaced short-lived pairing code

**Decision:** The extension obtains its dedicated token by submitting a **6-digit,
time-windowed pairing code** that the user reads from their own Kestrel instance
(`kestrel extension pair`, and available for the web UI to render later). The backend
validates the code (HMAC of the server secret over a 5-minute window) and mints a
distinct, stateless HMAC token that the extension stores and sends as a Bearer header.

**Why this over "exchange the existing AUTH_API_KEY":**
- `AUTH_ENABLED` is OFF by default, so most users have no `AUTH_API_KEY` to exchange —
  a code derived from a server-side secret works regardless of the auth toggle and still
  honors locked decision D-2 (always require a token, even on localhost).
- Keeps the extension token in a **separate secret space** from `AUTH_API_KEY` (locked
  decision D-1) — pairing never reveals or reuses the global key.
- Short-lived + possession-of-a-code proves local access to the instance, which is the
  real trust boundary for a self-hosted localhost service.

**Why stateless HMAC (no token table / no Alembic migration):**
- Foundation phase — a migration on the just-reconciled in-package Alembic history
  (G-1350) is avoidable risk. Pure functions are trivially unit-testable.
- Revocation in Phase 0 = rotate `EXTENSION_TOKEN_SECRET` (documented). A persisted,
  per-device revocable token store is a clean later-phase upgrade if multi-browser
  management is needed.

**Executor MUST nail:** the token secret is auto-generated and persisted so tokens
survive a backend restart (do NOT hold the secret only in a module global that resets
per process, or every restart silently un-pairs every extension).
</design_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| extension (chrome-extension://) → FastAPI | untrusted extension origin crosses into the API over localhost |
| any local process / any web page → localhost:8100 | CORS blocks reads, not simple-request side effects |
| pairing code → token mint | possession of the code authorizes minting a long-lived token |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-00-01 | Spoofing | `/api/extension/capture`,`/status` | mitigate | require dedicated extension token via `require_extension_token`; `hmac.compare_digest` verify; enforced even when AUTH_ENABLED=false |
| T-00-02 | Elevation | middleware `/api/extension/` bypass | mitigate | bypass ONLY skips the global AUTH_API_KEY check; per-route token dependency still gates capture/status; pair is code-gated |
| T-00-03 | Information disclosure | pair response | mitigate | return brand name "Kestrel" + version only; never echo AUTH_API_KEY or the token secret |
| T-00-04 | Tampering | extension token | mitigate | HMAC-signed token, `hmac.compare_digest`, reject malformed/truncated input |
| T-00-05 | Spoofing/CSRF | CORS for chrome-extension | mitigate | `allow_origin_regex` echoes a concrete 32-char extension origin (never `*`); frontend `allow_origins`/credentials untouched; custom Bearer header forces preflight |
| T-00-06 | Brute force | 6-digit pairing code | accept | localhost-only reachability + 5-min window + secret-derived; rate-limiting a code guess is a later-phase hardening if the endpoint is ever exposed remotely |
| T-00-07 | DoS | capture stub | accept | no DB write, no LLM call in Phase 0 — trivial cost |
</threat_model>
