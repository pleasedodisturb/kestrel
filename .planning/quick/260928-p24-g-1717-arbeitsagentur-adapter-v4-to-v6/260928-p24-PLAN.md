<objective>
G-1717: migrate the Arbeitsagentur integration off the retired `/pc/v4/jobs` endpoint (HTTP 403, re-verified by the planner on 2026-09-28) to `/pc/v6/jobs` (HTTP 200, same `X-API-Key: jobboerse-jobsuche`), in both the production adapter (`src/career_os/discovery/adapters.py`, `ArbeitsagenturAdapter`) and the standalone tool (`tools/germany_jobs.py`, which duplicates the same v4 parser). Parsers are rewritten for the v6 shape, proven against a recorded real v6 payload, and guarded by an opt-in live smoke test.

Purpose: Every discovery sweep currently gets a 403 from Arbeitsagentur, so Germany's largest public job board contributes zero rows (the discovery service turns the adapter exception into a warning, so nothing fails loudly).
Output: v6 adapter + tool, a trimmed real fixture, fixture-driven parser tests, an env-gated live smoke test, a registered `live` marker.

Planner-verified live facts (2026-09-28, recorded here so the executor does not have to rediscover them):
- v6 top-level keys: `ergebnisliste`, `maxErgebnisse`, `page`, `size`, `woOutput`, `facetten`. On zero hits the response has NO `ergebnisliste` key at all (`{"maxErgebnisse": 0, "page": 1, "size": 5, "woOutput": {...}}`).
- Per item: `stellenangebotsTitel`, `firma`, `referenznummer` (e.g. `12336-a26f539j0448996-S`), `hauptberuf`, `externeURL` (present on ~43% of items), `homeofficemoeglich` (true 18 / false 50 / key absent 32 in a 100-item sample), `stellenlokationen[0].adresse.{plz, ort, region, land}` with `land` = `DEUTSCHLAND` and `region` = `HESSEN` (ALL CAPS), `veroeffentlichungszeitraum.von` and `datumErsteVeroeffentlichung` (both `YYYY-MM-DD`). No hash-id field, no `refnr`, no `beruf`, no `arbeitgeber`, no `arbeitsort`.
- The adapter's existing params (`size`, `page=1`, `veroeffentlichtseit=30`, `angebotsart=1`, `was`, `wo`) are accepted by v6 (200). `page=0` is a 400, so keep 1-based paging.
- `arbeitszeit=ho` (the current remote filter) returns maxErgebnisse 0 on v6. A `homeoffice` param exists but every value tried (`true`, `1`, `ja`, `nv_true`, `prozentual`, `NACH_VEREINBARUNG`, `PROZENTUAL`, `MOEGLICH`, ...) is a 400 `Wert ungültig`; `homeofficemoeglich=true` is silently ignored. So remote filtering must move client-side.
- `https://www.arbeitsagentur.de/jobsuche/jobdetail/{referenznummer}` returns 200. The old v4-era detail URL form returns 404.

Claude's discretion (documented choices):
- Country de-capitalisation: an ALL-CAPS `land`/`region` value is converted with `str.title()` (so `DEUTSCHLAND` -> `Deutschland`, `HESSEN` -> `Hessen`); mixed-case values pass through unchanged; a missing `land` defaults to `Deutschland`. This keeps the location string byte-identical to the v4-era format (`Frankfurt am Main, Deutschland`), so stored rows and UI text do not change casing. Geo matching and dedup already lower-case, so this is presentation-only.
- `RawJobResult` has no `country` field and this plan does NOT add one (it is shared by every adapter and nothing downstream would consume it). Country is exposed through a pure helper returning `(city, country)` and embedded in `location`, and the tests assert both. The tool's dict output (free-form) gains explicit `country` and `remote` keys; `tools/scrape_resilient.py` already reads `j.get("remote", False)` from these dicts, so Arbeitsagentur rows start reporting remote correctly there.
- The tool keeps its own parser (it deliberately depends only on httpx) rather than importing the adapter's private helper; both parsers are tested against the SAME recorded fixture, which is the drift guard.
- Salary (`gehaltsspanneVon`/`gehaltsspanneBis`) is present in v6 but was never parsed under v4 and is not in the ticket; it stays out of scope.
</objective>
