# The Repo Coaching Masterlist

Three layers — **Technical**, **Operational**, **Marketing/Branding** — covering ~200 items that turn a public GitHub repo from "exists" into "thriving."

Each item has the same shape:

> **Item** — one-line _why_. Concrete artifact / link to a canonical example. Common pitfall.

A `·` prefix means "nice-to-have." Everything else is "default-yes for a serious public repo." If you skip a default-yes item, write down why.

> **Companions:**
> - To **act** on items: see [`QUICK-APPLY.md`](./QUICK-APPLY.md) (time-budgeted phases) + [`snippets/`](./snippets/) (copy-paste templates).
> - To **dig deeper** on any item: see [`research/`](./research/) — six topical deep-dives with WHY/HOW/PITFALL per item and citations.

## Layer 1 — Technical

Files, configs, automation. The stuff that lives in the repo.

### 1.1 Root files (community-health & legal)

- [ ] **`README.md`** — first impression and landing page. Do not bury install behind narrative. See Layer 3 for content rules.
- [ ] **`LICENSE`** — pick one and commit it as a real file (GitHub detects it from a top-level file, not a symlink). MIT/Apache-2.0 for permissive, AGPL-3.0/GPL-3.0 for copyleft, BUSL/Elastic for source-available. Use [choosealicense.com](https://choosealicense.com/). Pitfall: `LICENSE.md` (extension) sometimes confuses license detectors — prefer extensionless.
- [ ] **`CONTRIBUTING.md`** — how to set up dev env, run tests, commit style, PR expectations, "what we don't accept." Linked automatically by GitHub from the new-issue/PR flow. ([docs](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors))
- [ ] **`CODE_OF_CONDUCT.md`** — Contributor Covenant 2.1 is the default. Include real reporting contact (not "open an issue"). Pitfall: copying without filling in the contact email = signal of unseriousness.
- [ ] **`SECURITY.md`** — disclosure policy + private reporting channel. Enable [private vulnerability reporting](https://docs.github.com/en/code-security/security-advisories/guidance-on-reporting-and-writing/privately-reporting-a-security-vulnerability) so reports flow into a draft GHSA. Include supported versions table.
- [ ] · **`SUPPORT.md`** — where to ask questions (Discussions, Discord, Stack Overflow tag). Stops "questions" from clogging Issues.
- [ ] **`CHANGELOG.md`** — [Keep a Changelog](https://keepachangelog.com/) format, or auto-generated by [release-please](https://github.com/googleapis/release-please)/[changesets](https://github.com/changesets/changesets)/[semantic-release](https://github.com/semantic-release/semantic-release). Pitfall: a CHANGELOG that's auto-generated _from squashed PR titles_ — meaningless if titles aren't conventional.
- [ ] · **`CITATION.cff`** — for any repo that academics or researchers might cite. GitHub renders a "Cite this repository" button.
- [ ] · **`AUTHORS` / `MAINTAINERS.md`** — explicit list. CODEOWNERS handles routing; this handles credit and bus-factor visibility.
- [ ] · **`GOVERNANCE.md`** — once you have >1 maintainer, document decision-making, RFC process, and how someone becomes a maintainer.

### 1.2 Repo metadata (set in GitHub UI)

- [ ] **Description** (one line, in the "About" panel) — keyword-dense, action-first. "Self-hosted, AI-powered job-search platform" beats "Kestrel — a project."
- [ ] **Topics** — up to 20. Use the most-searched canonical ones (e.g. `cli`, `rust`, `self-hosted`, `llm`, `fastapi`). Browse [topic pages](https://github.com/topics) to see what's popular.
- [ ] **Homepage URL** — docs site or product page. Don't leave blank.
- [ ] **Social preview image** (1280×640) — Settings → Social preview. This is what Twitter/Slack/LinkedIn unfurl. Logo + tagline + readable at thumbnail size.
- [ ] **License detected** — confirm the green "License" badge is visible in the repo header. If GitHub can't detect it, fix the file.
- [ ] **Disable wiki** if unused (it just becomes a vector for spam). Use `docs/` instead.
- [ ] **Discussions** — enable if you want a Q&A space; otherwise route questions elsewhere via `SUPPORT.md`.
- [ ] **Sponsor button** — link via `.github/FUNDING.yml`.

### 1.3 Config & dotfiles

- [ ] **`.gitignore`** — language-specific. Use [github.com/github/gitignore](https://github.com/github/gitignore) templates. Audit for accidentally-committed `.env`, `dist/`, IDE files.
- [ ] **`.gitattributes`** — line endings (`* text=auto`), LFS rules, [linguist overrides](https://github.com/github-linguist/linguist/blob/main/docs/overrides.md) (e.g. mark `vendor/` as `linguist-vendored` so language stats are accurate).
- [ ] **`.editorconfig`** — cross-editor indent/charset. Two-line file beats half a year of style fights.
- [ ] · **`.tool-versions`** / **`mise.toml`** / **`.nvmrc`** / **`.python-version`** — pin runtime versions for [mise](https://mise.jdx.dev/) / asdf / nvm / pyenv users.
- [ ] **`.env.example`** — every env var the app reads, with safe placeholder values and inline comments. Never `.env` itself.
- [ ] · **`.dockerignore`** — mirrors `.gitignore` plus build artifacts; massive build-speed and image-size win.
- [ ] · **`.markdownlint.json` / `.vale.ini`** — if you have docs, lint the prose.

### 1.4 `.github/` directory

- [ ] **`.github/CODEOWNERS`** — auto-request reviews. Even solo maintainers benefit (sets expectations). Syntax: `* @username` for catch-all, then specific paths.
- [ ] **`.github/dependabot.yml`** — at minimum: every package ecosystem you use + `github-actions`. Group minor/patch updates to reduce PR noise.
- [ ] **`.github/FUNDING.yml`** — even if you only want one sponsor link. Renders a "Sponsor" button.
- [ ] **`.github/ISSUE_TEMPLATE/bug_report.yml`** — use [issue forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms) (YAML), not legacy markdown templates. Required fields: version, repro steps, expected, actual.
- [ ] **`.github/ISSUE_TEMPLATE/feature_request.yml`** — capture problem, proposed solution, alternatives, acceptance criteria.
- [ ] **`.github/ISSUE_TEMPLATE/config.yml`** — set `blank_issues_enabled: false` once your forms are good, plus `contact_links` (Discord, Discussions, Stack Overflow).
- [ ] **`.github/pull_request_template.md`** — short. What/Why/How tested/Screenshots/Linked issue. Long templates get ignored.
- [ ] · **`.github/PULL_REQUEST_TEMPLATE/`** (folder, multiple variants) — only if you actually need different PR types (e.g. `release.md`, `breaking-change.md`).
- [ ] · **`.github/release.yml`** — categorize auto-generated release notes by label. ([docs](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes))
- [ ] · **`.github/actions/<name>/action.yml`** — extract repeated workflow steps into composite actions inside the repo.

### 1.5 CI / GitHub Actions

- [ ] **Required status checks** (Settings → Branches) — lint, type-check, test, build. Don't gate on flaky e2e.
- [ ] **Pin actions by full SHA** (`actions/checkout@<40-char-sha>  # v4.1.7`) — tags are mutable; SHA is the only true immutable reference. ([wiz.io](https://www.wiz.io/blog/github-actions-security-guide), [GitHub changelog Aug 2025](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/))
- [ ] **Minimum permissions** — set `permissions: {}` at workflow root, then grant per-job (`contents: read`, etc.). Default token shouldn't have write access.
- [ ] **Concurrency groups** — `concurrency: { group: ${{ github.ref }}, cancel-in-progress: true }` on PR workflows so pushes cancel stale runs.
- [ ] **Caching** — `actions/cache` for deps; setup-* actions usually have `cache: true` shortcut.
- [ ] **Matrix builds** — across OS/runtime versions you actually claim to support. Don't matrix-test what you don't support.
- [ ] **Path filters** — `on.push.paths` + `on.pull_request.paths` to skip workflows that don't apply.
- [ ] **Reusable workflows** — extract repeated logic into `.github/workflows/_*.yml` with `workflow_call:` trigger.
- [ ] **OIDC for cloud deploys** — never store long-lived AWS/GCP/Azure keys as secrets. ([docs](https://docs.github.com/en/actions/deployment/security-hardening-your-deployments/about-security-hardening-with-openid-connect))
- [ ] **Lint workflows** — [actionlint](https://github.com/rhysd/actionlint) catches syntax + shell-injection. [zizmor](https://github.com/woodruffw/zizmor) catches security misconfigurations. Run both in CI.
- [ ] **Pinned runner labels** — `ubuntu-24.04` not `ubuntu-latest` for reproducibility. Pitfall: `latest` auto-upgrades and breaks builds.
- [ ] · **Workflow timeouts** — `timeout-minutes:` on every job. Default is 360 minutes (6 hours of credit drain when something hangs).
- [ ] · **Artifacts retention** — `retention-days: 7` on most artifacts. Default 90 wastes storage.
- [ ] · **Job summaries** — write to `$GITHUB_STEP_SUMMARY` for human-readable CI output (perf graphs, coverage diffs).

### 1.6 Security & supply-chain

- [ ] **Branch protection on `main`** — require PR, require status checks, require up-to-date branch, require linear history (if you squash), block force-push, require reviews from CODEOWNERS.
- [ ] **2FA / passkeys required** for org members. Settings → Authentication security.
- [ ] **Secret scanning + push protection** — free for public repos. Enable both. Configure custom patterns in `.github/secret_scanning.yml` for project-specific tokens.
- [ ] **CodeQL / SAST** — `.github/workflows/codeql.yml` from the GitHub-provided template. Schedule weekly + on PR.
- [ ] **Dependency review** — `actions/dependency-review-action` blocks PRs that introduce vulnerable deps.
- [ ] **Private vulnerability reporting enabled** (Settings → Security) — produces draft GHSA + private fork for fix collaboration. ([blog](https://github.blog/security/vulnerability-research/coordinated-vulnerability-disclosure-cvd-open-source-projects/))
- [ ] **Signed commits / tags** — GPG, SSH, or [gitsign](https://github.com/sigstore/gitsign) (Sigstore, keyless). Enforce via branch protection's "require signed commits."
- [ ] **OpenSSF Scorecard** — run the [scorecard-action](https://github.com/ossf/scorecard-action) weekly; enable "Publish results" so it appears on [scorecard.dev](https://scorecard.dev/). Aim for ≥7 then iterate. ([scorecard checks](https://github.com/ossf/scorecard/blob/main/docs/checks.md))
- [ ] · **OpenSSF Best Practices badge** — fill out the [questionnaire](https://www.bestpractices.dev/) for a passing/silver/gold badge.
- [ ] **SBOM** — generate CycloneDX or SPDX in CI; attach to releases. Enable GitHub's [auto-generated SBOM](https://docs.github.com/en/code-security/supply-chain-security/understanding-your-software-supply-chain/exporting-a-software-bill-of-materials-for-your-repository) (Insights → Dependency graph → Export SBOM).
- [ ] **SLSA provenance** — for releases, generate `*.intoto.jsonl` via [slsa-github-generator](https://github.com/slsa-framework/slsa-github-generator). Scorecard rewards this.
- [ ] **Build attestations** — `actions/attest-build-provenance` + sigstore for npm/PyPI/container artifacts.
- [ ] · **Reproducible builds** — for security-critical projects, document the build env so others can rebuild bit-identical artifacts.
- [ ] · **Container image scanning** — Trivy / Grype / Snyk on every image build. Distroless/Chainguard base images cut CVE noise.
- [ ] · **License scanning** — [licensee](https://github.com/licensee/licensee) or [scancode](https://github.com/nexB/scancode-toolkit) on dependencies; block GPL infiltration in MIT projects (or vice versa).

### 1.7 Versioning & releases

- [ ] **SemVer** — `MAJOR.MINOR.PATCH`. Stick to it religiously after 1.0; document the pre-1.0 contract explicitly. ([semver.org](https://semver.org/))
- [ ] **Conventional Commits** — `feat:`, `fix:`, `feat!:` for breaking. Enforced by [commitlint](https://commitlint.js.org/) in pre-commit + CI.
- [ ] **Release automation** — pick one and commit:
  - JS: [changesets](https://github.com/changesets/changesets) (best for monorepos), [semantic-release](https://github.com/semantic-release/semantic-release).
  - Polyglot: [release-please](https://github.com/googleapis/release-please) (Google) — works for Python/Rust/Go/JS/etc.
  - Rust: [cargo-release](https://github.com/crate-ci/cargo-release).
- [ ] **Signed release artifacts** — sigstore-sign or GPG-sign tarballs/binaries; publish `.sig` + `SHA256SUMS` next to artifacts.
- [ ] **Reproducible release notes** — categorized by label via `.github/release.yml`, or by commit type via release-please.
- [ ] **Pre-release channels** — `next`/`canary`/`beta` tags so users can opt in.
- [ ] **Deprecation policy** — written. "Deprecation warning ≥1 minor, removal in next major."
- [ ] · **Release captain rotation** — if you have multiple maintainers, document the rotation.
- [ ] · **LTS policy** — only if you have the bandwidth. Otherwise say "we don't do LTS" explicitly.

### 1.8 Quality automation

- [ ] **Pre-commit framework** — [pre-commit.com](https://pre-commit.com/) (polyglot) or [lefthook](https://github.com/evilmartians/lefthook) (faster). Hooks: format, lint, secret-scan (gitleaks), typo-check (typos), commitlint.
- [ ] **Linter + formatter per language** — Python: ruff (does both). JS/TS: biome or eslint+prettier. Rust: clippy + rustfmt. Go: golangci-lint + gofumpt.
- [ ] **Type checker** — mypy/pyright for Python, tsc strict for TS. CI fails on type errors.
- [ ] **Coverage reporting** — codecov.io / coveralls / [coverage-comment](https://github.com/marketplace/actions/python-coverage-comment). Don't enforce a coverage % — measure trends, not absolutes.
- [ ] · **Mutation testing** — [stryker](https://stryker-mutator.io/) / [mutmut](https://github.com/boxed/mutmut) on critical modules. More signal than coverage.
- [ ] · **Snapshot / visual regression** — for UIs: Playwright / Chromatic / Percy.
- [ ] · **Property-based tests** — Hypothesis (Python), fast-check (TS), proptest (Rust) for parsers/algorithms.
- [ ] · **Benchmarks in CI** — [bencher.dev](https://bencher.dev/) / [hyperfine](https://github.com/sharkdp/hyperfine) for perf-critical projects.
- [ ] · **Bundle size budget** — [size-limit](https://github.com/ai/size-limit) for JS libs; fails PR if budget exceeded.

### 1.9 Documentation

- [ ] **Quickstart** — copy-pasteable, <60 seconds to first useful output. Pitfall: hiding install instructions behind narrative.
- [ ] **`docs/`** folder — structured per [Diátaxis](https://diataxis.fr/): tutorials (learning), how-to (task), reference (lookup), explanation (understanding). Mixing them is the #1 docs-quality bug.
- [ ] **API reference** — auto-generated. OpenAPI for HTTP APIs, TypeDoc for TS, Sphinx for Python, rustdoc for Rust.
- [ ] **Architecture page** — one diagram + one paragraph per major component. Mermaid renders natively in GitHub.
- [ ] **ADRs** (Architecture Decision Records) — `docs/adr/0001-use-sqlite.md`. [adr-tools](https://github.com/npryce/adr-tools).
- [ ] · **RFC process** — `docs/rfcs/` for proposals before implementation. Rust/React/Ember have great templates.
- [ ] **`examples/`** — runnable, kept in CI. Stale examples are worse than no examples.
- [ ] **`docs/` site** — Docusaurus / mkdocs-material / VitePress / Mintlify / Astro Starlight. Hosted on the project's own domain. Cf. [stripe.com/docs](https://stripe.com/docs), [supabase.com/docs](https://supabase.com/docs).
- [ ] · **`llms.txt`** — Markdown-formatted index of canonical docs URLs at site root for LLM agents. Adoption rising; cost is near-zero. ([gitbook](https://www.gitbook.com/blog/what-is-llms-txt))
- [ ] · **`/llms-full.txt`** — concatenated full docs corpus, for one-shot ingestion by LLMs.
- [ ] · **Search** — Algolia DocSearch (free for OSS) or built-in MeiliSearch.

### 1.10 Dev environment

- [ ] **`.devcontainer/devcontainer.json`** — works in VS Code + Codespaces. One-click onboarding.
- [ ] · **Codespaces prebuild** — Settings → Codespaces → Set up prebuild. <30 second cold start.
- [ ] · **Gitpod** — `.gitpod.yml` for a second cloud-IDE option.
- [ ] **`docker-compose.yml`** for dev — one command to bring up the whole stack.
- [ ] **`Makefile` / `justfile` / `Taskfile.yml`** — one place for "scripts to rule them all": `make setup`, `make dev`, `make test`, `make lint`, `make release`. ([GitHub's pattern](https://github.blog/engineering/scripts-to-rule-them-all/))
- [ ] · **`scripts/bootstrap`** — idempotent first-time setup. Detects OS, installs deps.

### 1.11 Testing

- [ ] **Unit / integration / e2e** split — directory or pytest-marker convention. Document which run on PR vs nightly.
- [ ] **Fixtures factored** — not copy-pasted across files.
- [ ] **Flaky-test quarantine** — separate marker/dir; runs but doesn't block PRs.
- [ ] **Coverage delta on PR** — fail PR if coverage drops >X%.
- [ ] · **Mutation testing** on critical modules (see 1.8).
- [ ] · **Performance regression tests** (see 1.8).

### 1.12 A11y / i18n / perf (UI projects)

- [ ] **A11y in CI** — axe-core / pa11y / Lighthouse-CI.
- [ ] **Lighthouse CI** — performance budget per route.
- [ ] · **i18n strategy** — even if currently English-only, document the path to localization.

### 1.13 Monorepo (if applicable)

- [ ] **Workspace tool** — pnpm/yarn workspaces, Turborepo, Nx, Bazel, cargo workspaces.
- [ ] **Affected-only builds** — Turborepo `--filter`, Nx `affected`, Bazel.
- [ ] **Per-package versioning** — changesets if you publish multiple npm packages.

## Layer 2 — Operational

How maintainers _run_ the repo: triage, reviews, releases, community, governance. Most repos die here, not at the technical layer.

### 2.1 Issue management

- [ ] **Triage cadence** — weekly at minimum. Solo maintainers: 30 min/Mon. Bigger projects: rotation. Untriaged-issue count is your bus factor.
- [ ] **Label taxonomy** — small and orthogonal:
  - `type/*`: bug, feature, docs, chore, security
  - `area/*`: api, frontend, ai-providers, etc. (project-specific)
  - `priority/*`: p0–p3 (don't go finer)
  - `status/*`: needs-info, needs-repro, blocked, wontfix
  - `good first issue`, `help wanted` (canonical, GitHub special-cases them)
- [ ] **Saved triage filters** — pin a "needs triage" view in Insights or a Project board.
- [ ] **Issue forms over markdown templates** — required fields, dropdowns, version pickers stop bad reports at the door.
- [ ] **"Minimal repro" rule** — written in CONTRIBUTING. Close-with-template if not provided after N days.
- [ ] **Stale bot — carefully.** [actions/stale](https://github.com/actions/stale) helps a flooded repo but alienates contributors when misconfigured. Rules: long timeout (≥90 days inactive), only on `needs-info`, easy un-stale via comment, never auto-close `bug` or `security`. Many top-tier projects have removed stale bots ([discussion](https://github.com/orgs/community/discussions/163134)).
- [ ] **Discussions vs Issues** split — Q&A and "is this a bug?" go to Discussions; confirmed bugs and tracked work go to Issues.
- [ ] **Locking** old threads — automatic after 30 days inactivity on closed issues stops necro-comments.

### 2.2 PR workflow

- [ ] **Small PRs** — <400 LOC is the well-cited threshold above which review quality drops sharply ([SmartBear study](https://smartbear.com/learn/code-review/best-practices-for-peer-code-review/)). Document this.
- [ ] **Draft PRs** by default for in-progress work; mark ready-for-review explicitly.
- [ ] **PR description requirements** — what/why/how-tested/screenshots/linked-issue. Use the template.
- [ ] **Self-review checklist** — author reviews their own diff first. Catches half the comments.
- [ ] **Conventional Commit PR titles** — combined with squash-merge gives you a clean changelog for free. Enforce via [action-semantic-pull-request](https://github.com/amannn/action-semantic-pull-request).
- [ ] **Squash-merge default** — clean main history; PR body becomes the squash commit body. (Some projects prefer rebase-merge — pick one and be consistent.)
- [ ] **Merge queue** — once you have ≥5 PRs/day, [GitHub Merge Queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) prevents semantic conflicts ("PR A passes, PR B passes, A+B fails").
- [ ] **Auto-merge** for Dependabot patch/minor when CI green + label.
- [ ] **CODEOWNERS reviews** required for sensitive paths (auth, billing, db migrations).
- [ ] **Review SLA** — set a public expectation. "We aim to triage within 7 days, review within 14." Beats silent backlog.
- [ ] **Review tone** — use [conventional-comments](https://conventionalcomments.org/) (`nit:`, `suggestion:`, `issue:`, `praise:`). Distinguishes blocking from preference.
- [ ] · **Trunk-based development** — short-lived feature branches, no long-running release branches unless you ship multiple versions in parallel. ([trunkbaseddevelopment.com](https://trunkbaseddevelopment.com/))

### 2.3 Branching & releases

- [ ] **`main` is the default branch** and protected.
- [ ] **Release strategy** — pick one and document:
  - **Continuous** (release on every merge to main, fully automated).
  - **Time-based** (every Tue, every 1st of month).
  - **Feature-based** (when feature X lands).
- [ ] **Hotfix flow** — written. Branch from latest tag, fix, tag, cherry-pick to main.
- [ ] **Breaking-change communication** — release note, blog post, deprecation warning ≥1 minor cycle prior.
- [ ] **Migration guides** for every major. Concrete code diffs, not prose.
- [ ] **Version skew** — for client/server projects, document compatibility matrix.

### 2.4 Governance

- [ ] **Solo-maintainer reality check** — most OSS is one person. Document that openly. Set expectations on response time.
- [ ] **Maintainer onboarding** — written process. How a frequent contributor becomes a committer.
- [ ] **Maintainer offboarding** — equally important. How to step down without burning the project.
- [ ] **Decision-making** — lazy consensus (no objections within N days = approval) for most projects. Document it.
- [ ] · **RFC process** — for changes that affect public API or architecture. Rust's [RFC repo](https://github.com/rust-lang/rfcs) is the canonical model.
- [ ] · **Public roadmap** — a GitHub Project board, a `ROADMAP.md`, or a Linear/Plane/Notion view. Up-to-date or deleted; nothing in between.
- [ ] · **Quarterly goals** — public, with retrospective. Builds trust.
- [ ] · **Open meetings / office hours** — recorded, on YouTube. Even monthly is enough.

### 2.5 Community health

- [ ] **CoC enforcement path** — named contact, response SLA, escalation. Without this CoC is theatre.
- [ ] **Welcoming first contributors** — [first-interaction action](https://github.com/actions/first-interaction) or [welcome-bot](https://probot.github.io/apps/welcome/) posts a friendly comment.
- [ ] **`good first issue` curation** — at least 5 well-scoped at all times. Real bugs, not invented work.
- [ ] **all-contributors bot** — [allcontributors.org](https://allcontributors.org/) — recognizes non-code contributions too.
- [ ] **Community channel** — Discord (most popular for dev tools), Slack (declining for OSS), Matrix (FOSS-aligned), Discourse (long-form). Pick one.
- [ ] · **Community manager** — once Discord has >500 members. Even part-time.
- [ ] · **Recognition rituals** — monthly contributor highlights, swag for first PR, conference shout-outs.

### 2.6 Contributor experience

- [ ] **"Your first PR" doc** — concrete, video-walkthrough preferred. Cf. [first-contributions](https://github.com/firstcontributions/first-contributions).
- [ ] **`good first issue` should genuinely take <2 hours** — if it takes longer, it's `help wanted`, not `good first issue`.
- [ ] **DCO over CLA** unless you have a strong legal reason. [DCO](https://developercertificate.org/) is `git commit -s`; CLAs deter contributors.
- [ ] **Contributor ladder** — written: contributor → reviewer → maintainer → owner. Promotion criteria explicit.
- [ ] **Pair-programming office hours** — even monthly. Best converter of drive-by contributors into regulars.

### 2.7 Bots & automation (operational)

- [ ] **Dependabot / Renovate** — pick one. Renovate is more powerful (group rules, schedules); Dependabot is GitHub-native and zero-config.
- [ ] **all-contributors bot** — see 2.5.
- [ ] **size-label bot** — labels PRs by LOC. Encourages small PRs.
- [ ] **mergify / kodiak** — auto-merge on conditions (CI green, approved, label).
- [ ] · **danger.js / danger-python** — script PR-level checks ("did you update CHANGELOG?", "is the PR description filled in?"). Lighter than a custom Action.
- [ ] · **probot apps** — custom logic without your own server.

### 2.8 Metrics & health

- [ ] **Monitor weekly**: open issues age, time-to-first-response, time-to-close, PR merge time, ⭐/week, weekly active contributors.
- [ ] **OpenSSF Scorecard score** trend.
- [ ] **GitHub Insights** — Code Frequency, Contributors, Community profile (Settings → Insights → Community Standards = built-in checklist).
- [ ] **Star history graph** ([star-history.com](https://star-history.com/)) — embed in README at >1k ⭐.
- [ ] **CHAOSS metrics** ([chaoss.community](https://chaoss.community/)) — bus factor, lottery factor, time-to-merge, contributor absence.
- [ ] **Repo Insights → Traffic** — referrer breakdown shows what's actually working for marketing.
- [ ] · **Plausible/Fathom on docs** — privacy-respecting, lightweight.

### 2.9 Hard cases

- [ ] **Entitled users** — boilerplate response saved as a [saved reply](https://docs.github.com/en/get-started/writing-on-github/working-with-saved-replies/about-saved-replies). "We can't accept this; here's why."
- [ ] **Drive-by PRs** that don't follow CONTRIBUTING — automated reply pointing at the doc; close after N days no response.
- [ ] **Toxic comments** — [Hide as off-topic / abusive], block user, lock thread. Document the policy in CoC.
- [ ] **Trademark / fork issues** — register name early; have a TRADEMARK.md if name is enforceable.
- [ ] **CVE coordination** — private GHSA → fix in private fork → coordinate disclosure date with reporter → release with advisory → request CVE via GHSA. ([blog](https://github.blog/security/vulnerability-research/coordinated-vulnerability-disclosure-cvd-open-source-projects/))
- [ ] **Embargo discipline** — no public PRs, no public issue comments, no Discord leaks until disclosure date.

### 2.10 Burnout prevention

- [ ] **Pinned issue: "Project scope and what we don't accept"** — saves rejection arguments.
- [ ] **Schedule "no maintenance" weeks** — public, in your roadmap.
- [ ] **Bots do the grunt work** — labeling, formatting, dep updates. If you're doing it twice, automate it.
- [ ] **Saying no is a feature** — most popular OSS reject more than they accept. Be explicit and kind.
- [ ] **Succession plan** — at minimum, one other person with org-admin rights. Bus factor 1 is a project-killer.

### 2.11 Sponsorship & funding

- [ ] **GitHub Sponsors** profile — fill it out fully (tiers, goals, recent activity).
- [ ] · **Open Collective** — better for transparent fund accounting + multi-maintainer payouts.
- [ ] · **Polar.sh** — pays per-issue bounties from sponsors.
- [ ] · **Tidelift** — enterprise contracts for "promised maintenance."
- [ ] · **Dual-license / open-core** — only if you've thought hard about it. Pitfall: half-rugging the community by closing features post-popularity.
- [ ] · **`FUNDING.yml`** — see 1.4.

## Layer 3 — Marketing, Branding, Discovery

The single highest-leverage layer for most public repos. Most engineers under-invest here.

### 3.1 Identity

- [ ] **Name** — short, pronounceable, distinct, _searchable_. Test: "[name] github" and "[name] [category]" should not collide with a giant brand. Trademark check: USPTO TESS / EUIPO / a quick Google.
- [ ] **One-liner** — `<verb> <thing> for <who>`. "Self-hosted, AI-powered job-search platform" parses in 1 second.
- [ ] **Tagline** — 5–7 words, memorable. "Don't make me think." "Postgres, but YAML."
- [ ] **Logo** — light + dark variants, SVG. Sized for favicon (16×16) and OG image (1280×640). Cf. [supabase logos](https://github.com/supabase/supabase/tree/master/apps/www/public/img).
- [ ] **Brand colors** — 1 primary, 1 accent, neutrals. Document in `docs/branding/`.
- [ ] **Domain** — `.dev`, `.com`, `.io` in that order of preference for technical brands. `.com` for B2B-ish.
- [ ] **Package name** — namecheck npm/PyPI/cargo/Homebrew before committing to a name.

### 3.2 README hero (the top viewport)

What a visitor sees in the first 3 seconds determines bounce rate.

- [ ] **Centered logo** — light/dark via [GitHub picture-element trick](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#specifying-the-theme-an-image-is-shown-to).
- [ ] **One-sentence pitch** in `<strong>` directly under the logo.
- [ ] **Hero artifact** — pick ONE: animated terminal cast ([asciinema](https://asciinema.org/) / [vhs](https://github.com/charmbracelet/vhs)), product GIF (≤3 MB), or screenshot. No mystery banners.
- [ ] **Try-it-in-30-seconds CTA** — copy-pasteable command, immediately. Pitfall: hiding install behind a TOC.
- [ ] **Badges** — pick 3–5 max:
  - CI status (passing/failing)
  - Latest release / version
  - License
  - Sponsors / Discord member count
  - OpenSSF Scorecard
  Skip: "made with love", build-tool logos, every star count badge ever.
- [ ] · **"Open in Codespaces" / "Try in Replit" button** — friction-killer.

### 3.3 README body

- [ ] **Quickstart first** — _not_ "About this project" first.
- [ ] **Features** — bulleted, with screenshots/icons. Each feature must answer "why I care."
- [ ] **Comparison table** vs alternatives. Honest. "X is better at A; we're better at B." Most useful section in any popular OSS README.
- [ ] **Architecture diagram** (Mermaid in-line, or PNG) — even one box-and-arrows.
- [ ] **Use-cases** with concrete examples or links to "X built with Y."
- [ ] **"Who uses X"** wall of logos — even 3 logos is a credibility boost. Get permission first.
- [ ] **Testimonials** — 1–3 real quotes with names and roles. Don't fake.
- [ ] **Roadmap snippet** — link to a public Project board, not a static list that goes stale.
- [ ] **Star history** — embed [star-history.com](https://star-history.com/) chart once you cross 1k ⭐.
- [ ] **Community links** — Discord, Discussions, Twitter/X, Bluesky.
- [ ] **Sponsors section** — even if just "Become the first."
- [ ] **License + contributing** — short pointers, with links.
- [ ] **No TOC** unless the README is >500 lines. TOCs on short READMEs are noise.

### 3.4 Visual assets

- [ ] **Social preview image** — 1280×640. Logo + tagline + readable at 200px-wide thumbnail. Use [og-image.vercel.app](https://og-image.vercel.app/) or Figma.
- [ ] **Per-page OG images** on docs site — Astro/Next.js have generator plugins.
- [ ] **Consistent screenshot style** — same browser chrome, same padding, dark mode often pops harder. Cf. [stripe.com](https://stripe.com/).
- [ ] **Code screenshots** — [carbon.now.sh](https://carbon.now.sh/), [ray.so](https://ray.so/), [tetragon.so](https://tetragon.so/) for nicer code blocks in social posts.
- [ ] · **Loom / Tella walkthrough** — 90 seconds. Embed in README or link.
- [ ] · **Brand kit** — Figma file, a `docs/branding/` page, downloadable logos.

### 3.5 GitHub-side discovery

- [ ] **Topics** — see 1.2. Audit by browsing [github.com/topics](https://github.com/topics).
- [ ] **Description** — keyword-rich. GitHub search ranks on this.
- [ ] **Pinned repos** on personal/org profile.
- [ ] **Org profile README** — `.github/profile/README.md` in a `.github` repo at org level.
- [ ] **GitHub Trending** — depends on star velocity over a 24–48 hour window. You can't game it; you can stack a launch around it (3.10).
- [ ] · **GitHub Stars program** — apply if you're an active maintainer; gives you visibility lifts.

### 3.6 External discovery

- [ ] **Awesome-* list inclusion** — `awesome-<your-language>`, `awesome-<your-domain>`, `awesome-self-hosted`. Open a PR with the standard format.
- [ ] **Alternative-to / SaaSHub / StackShare / Slant** — list yourself; comparison pages drive long-tail SEO.
- [ ] **Newsletters & curated feeds**:
  - [TLDR Newsletter](https://tldr.tech/), [console.dev](https://console.dev/), [bytes.dev](https://bytes.dev/), [Hacker Newsletter](https://www.hackernewsletter.com/), [Changelog Weekly](https://changelog.com/weekly), [This Week in [language]](https://this-week-in-rust.org/) etc.
  - Cold-pitch a 2-paragraph blurb. They love good projects.
- [ ] **Reddit** — pick the right subreddit (`/r/selfhosted`, `/r/programming`, `/r/<language>`). Have karma first; read each sub's rules.
- [ ] **Hacker News "Show HN"** — Tuesday 8–10 am PT is folklore-optimal. Be present in comments for the first 4 hours; that's when ranking happens. Honest title; no clickbait.
- [ ] **Lobsters** — invite-only; quality skews up. A good "Show HN" alternative once invited.
- [ ] **Product Hunt** — mostly relevant for SaaS-ish OSS with a hosted version. Tuesday/Wednesday launches, hunter optional. ([playbook](https://dev.to/iris1031/product-hunt-launch-playbook-the-definitive-guide-30x-1-winner-1pbh))
- [ ] **dev.to / Hashnode crossposts** — canonical URL pointing at your blog.
- [ ] **Indie Hackers** for B2B/SaaS-flavored launches.

### 3.7 SEO & docs-as-marketing

- [ ] **Docs on your own domain** — `docs.yourproject.com`, not just GitHub README. Compounds for SEO.
- [ ] **Sitemap + robots.txt + Open Graph + canonical URLs** — table stakes.
- [ ] **Schema.org** — `SoftwareApplication`, `FAQ`, `HowTo` JSON-LD.
- [ ] **Comparison landing pages** — `/vs/competitor`, `/migrate-from-x`. SEO gold for category leaders. Cf. Supabase's vs-Firebase pages.
- [ ] **Audience-targeted landings** — `/for-django`, `/for-data-scientists`. Each one gets its own README example + tutorial.
- [ ] **Tutorial SEO** — "How to [common task] with [your project]" posts. [Stripe's docs](https://stripe.com/docs) school of thought.
- [ ] · **`llms.txt` + `llms-full.txt`** — see 1.9. Adoption growing; cost is near-zero. ([gitbook](https://www.gitbook.com/blog/what-is-llms-txt))

### 3.8 Content marketing

- [ ] **Launch blog post** — problem → solution → demo → call to action. Bury it in your release post if you don't want a separate one.
- [ ] **Weekly/monthly changelog post** — even a tweet-sized "what shipped this week."
- [ ] **Engineering deep-dives** — the gold standard for OSS marketing. Cf. [planetscale.com/blog](https://planetscale.com/blog), [supabase.com/blog](https://supabase.com/blog), [fly.io/blog](https://fly.io/blog).
- [ ] **Conference talks** — submit to language-specific confs. Even a 5-min lightning talk.
- [ ] **Podcast appearances** — pitch a 1-paragraph "why this is interesting." Changelog, Software Engineering Daily, Latent Space.
- [ ] **YouTube demos** — 90-second demos travel further than blog posts in 2026.
- [ ] · **Live-streams** — Twitch / YT. Build-in-public has long tail.
- [ ] · **Tiny tutorial threads** — 5-tweet micro-tutorials hit hard on X/Bluesky.

### 3.9 Social

- [ ] **Project handle on X/Bluesky/Mastodon/LinkedIn** — same name everywhere; namecheck.
- [ ] **Profile basics**: bio, link to repo + docs, banner, pinned launch tweet.
- [ ] **Founder personal brand** matters as much as the project handle for early-stage; transition over time.
- [ ] **Build-in-public threads** — milestones, screenshots, before/after.
- [ ] **Reply-guy strategy** — comment on adjacent OSS / category-leader posts with substance. Free distribution.
- [ ] · **Memes** — sparingly. Brand-appropriate.
- [ ] · **Milestone posts** — 1k ⭐, 10k ⭐, 100 contributors. Always plan a small content piece around them.

### 3.10 Launch choreography

- [ ] **Pre-launch (4–6 weeks)** — waitlist landing, design partners, teaser content, list 3–5 "launch buddies" willing to amplify.
- [ ] **Launch day** — coordinate (within 2 hours):
  - HN "Show HN" post
  - r/<niche> Reddit post
  - X/Bluesky/Mastodon thread
  - Discord/Slack/Matrix announcement to allied communities
  - Newsletter mention (pre-arranged)
  - Product Hunt (only if SaaS-ish)
- [ ] **Be present in HN comments for 4 hours.** Engagement weight is highest there. Don't be defensive.
- [ ] **Post-launch (week 1–2)** — follow-up "what we learned" post, address top feedback, ship a small update labeled with the launch.
- [ ] **Don't buy stars.** You'll get caught and it's career-staining.

### 3.11 Differentiation

- [ ] **Explicit "not X"** — "We are not a Kubernetes replacement." Subtractive positioning is the highest-leverage move for niche projects.
- [ ] **"X for Y" template** — "Stripe for healthcare," "Postgres for time series." Compresses positioning to 4 words.
- [ ] **Wedge feature** — one thing you do dramatically better. Lead with it everywhere.
- [ ] **10× claim with proof** — benchmarks linked, methodology open, reproducible. Pitfall: vague "fast" / "modern" claims.

### 3.12 Anti-patterns

- [ ] No badge soup (>5 badges).
- [ ] No TOC for short READMEs.
- [ ] No missing install instructions in the first viewport.
- [ ] No screenshots → automatic credibility tax.
- [ ] No jargon-dense first paragraph.
- [ ] No "production-ready" / "blazingly fast" without proof.
- [ ] No clone-of-clone positioning ("X but with [tiny tweak]").
- [ ] No buying stars / astroturfing.

### 3.13 Measurement

- [ ] **Star velocity** (⭐/week, not absolute count).
- [ ] **GitHub Insights → Traffic** — referrer breakdown weekly.
- [ ] **Plausible/Fathom** on docs site.
- [ ] **UTM conventions** for every link you publish.
- [ ] **Conversion funnel** — visitor → docs → install → first useful output. Each step's drop-off is fixable.
- [ ] **Newsletter open / click rates**.
- [ ] **Discord weekly active members**.
- [ ] · **Annual public retro** — published, with the embarrassing parts.

## Cross-layer principles

- **Default-yes vs nice-to-have.** Items without `·` are default-yes for any serious public repo. If you skip one, write down why in your repo's `docs/decisions/`.
- **Compound, don't accumulate.** A great README is worth 10 mediocre items elsewhere. Do fewer things, better.
- **Automate the chores.** Every step a human does on every PR/release is a step a bot should do.
- **Optimize for the next contributor's first 60 seconds.** Most of this list is about reducing time-to-first-confused-question.
- **Marketing is leverage; security is base rate.** Unsecured popular project = liability. Insecure unknown project = no impact. Secure unknown project = invisible. Aim for both.
